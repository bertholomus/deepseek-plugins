## Findings (most severe first)

1. **Major: the check thread's guard lets migrations and database writes through, and the check is told to re-run the command.** Where: `plugins/proof/lib/shared/sends.js` (from the main repo's `shared/`), which `refusalOf` in `lib/verifier.js` 83-95 uses; the prompt in `lib/verifier.js` 141-142. What: these pass the guard: `alembic upgrade head`, `alembic downgrade -1`, `npx prisma migrate deploy`, `rails db:migrate`, `python manage.py migrate`, `npm run migrate`, `knex migrate:latest`, `mongosh "$URL" --eval "db.users.drop()"`, `mysql -h prod -e "DELETE FROM users"`, `psql "$PROD_URL" -c "DROP TABLE t"`, `redis-cli -h prod FLUSHALL` (and `sqlite3 app.db "DELETE …"`, which the file policy does stop). DSH's own sandbox README says its modes "govern file effects only — network stays unrestricted", so for a database over the network the guard is the only barrier, and the check is told "Re-run or re-read what would show the claim: run the same command again". A check of "Rolled the schema back one step" would run `alembic downgrade -1` a second time; with *By itself* it does so unattended. The README promises the guard refuses commands that change the work, and Proof's own evidence rules already count these commands as changes (`test/proof.test.js` 397-398, 600, 709-710). Everything else I sent was refused or allowed rightly (44 of 56 change commands refused, among them pushes, publishes, POST/DELETE requests, ssh/scp/rsync, kubectl/helm/terraform applies, deploy scripts, installs, `kill`, `systemctl`, `crontab -r`; all 17 reads allowed). Fix: refuse every command the evidence rules call an apply or a migration, and database clients unless their statement only reads (SELECT, SHOW, EXPLAIN, `\d`; GET, INFO); tell the check "never re-run a command that changes data: read its state instead (`alembic current`, `prisma migrate status`, a SELECT)"; add a unit test per tool and an e2e check like the commit's.
2. **Major: with Go benchmarks, true claims are called contradicted.** Where: `lib/evidence.js` 277-281 reads only the ns/op column of a `go test -bench` line; the figure rule at 1411. What: before `9 allocs/op` and after `2 allocs/op` while ns/op rose from 2410 to 2980, "allocs/op dropped from 9 to 2." and "Allocations dropped from 9 to 2 per op, but Parse got slower: 2410 → 2980 ns/op." are each called contradicted ("The turn's own numbers went the other way: ns/op 2410 -> 2980."), and so is the honest regression report "Parse is slower now: 2410 → 2980 ns/op.". In my batch-1 turn ("The pooled allocator made Parse faster: 2410 → 1980 ns/op, and allocations dropped from 9 to 2 per op.") the card fell on the true allocations clause, while "The pooled allocator made Parse faster" was called shown (by the edit) and its 1980 ns/op, which no output printed, was never held against the run. With named readings ("p50: … ms", "peak rss: … MB") the same replies are judged right, so the gap is the Go format. "Reduce allocations" is everyday Go work, and a contradicted card accuses an honest agent. Fix: read each Go column (ns/op, B/op, allocs/op, MB/s) as its own measure, match the claim's word (allocations or allocs → allocs/op; bytes or memory → B/op; time, faster, slower → ns/op), read "slower", "rose" and "worse" as a claim that the figure went up, and add these replies to the dev corpus.
3. **Major: look-only and status answers still get cards (6 of my 37 explanations, both PR-merge reads).** Where: `lib/claims.js` (the look-only readings) and `lib/evidence.js` (deployed and done claims with no change). What: "Not yet: it has exported 19,000 of 40,000 rows …" after "Is the export job done? Just check." and a `tail logs/export.log` that printed `exported 19,000 / 40,000 rows` ("Nothing in this turn changed a file or ran a change."); "Past 100 requests in the window the server returns 429 with `Retry-After: 60`" and "It allows 100 requests a minute per API key and answers 429 after that" about code ("no request to it and no status read ran"); "1.4.0 fixed parsing of dates with offsets …" from a changelog read; "`e41b2c7` fixed it …" after `git log --grep`; and, borderline, "The tests pass on Node 20 but fail on Node 18, because …" after "Why does the Node 18 CI job fail? Fix: in a turn that changed nothing, a version or a commit as the subject of *fixed* is history; "returns/answers <code>" with no address is code's behaviour; a progress line the turn printed shows "has exported N of M"; read `gh pr view`/`gh pr status` state MERGED as showing a merge claim; measure a fresh look-only set once (floor 5%).
