## Gotchas
- DSH's gateway serves a window endpoint only when its method is marked as `@Remote` would mark it: every suite `remote.js` ends with `markRemote(Class, [...every method])`; `test/suite-shared.test.js` fails when one is missing. Throw `RemoteError` (via the class's `run`) so the window gets the message.
- DSH quits on SIGTERM at once (about 75 ms) without closing running turns; the next start closes them as `interrupted`. A quit and a crash look the same afterwards, so the words say "a quit, a restart or a crash".
- After a failed goal round, its `<goal_round>` message stays "fresh" beside the next one in the model's input: the scripted model reads the newest `Round: N/`.
- The bench runs DSH in DSH's default permission mode (the goal and todo tools need no approval); do not set a full-access mode there.
- Helpers: `dshlane` does not know this project; use `~/.local/bin/dshb new --ws ~/Projects/dsh-plugin-suite --provider owner-ascents --model GLM-5.3-Flash-EXL3 --effort max --title "[Flash] · <task>" --text-file <brief>` and `dshb wait SID`. Do not edit shared tools in `~/.local/bin`.
- The naming scan in `test/coordinator.test.js` covers every text file except `HANDOFF.md` (and now `briefs/`): no vendor assistant names anywhere else, commit messages included. Tests that check for such names use `OTHER_NAMES` from `test/helpers/client.mjs` (built in pieces).
- Shared code: edit `shared/host/*.js` or `shared/client-kit.js`, then `node scripts/sync-shared.mjs`; never edit a plugin's `lib/shared/` copy or its kit block by hand.
- Plugins' `index.js`/`remote.js` import DSH packages, which the repo has no `node_modules` for: unit tests import only the pure modules; the wiring is proven by the real-DSH e2e.
- DSH's agent events put the agent in the payload (`({ agent, status })`); `agent/created` is a serial event, so its listener must never return a promise that blocks (ours are wrapped in `guard`).

## Gotchas (things that broke, decisions made and why)
- **DSH's new-chat screen** (its hero): a chat shows it until its first `turn/start` clears `sessionListMetadata.blank`; commands (`/coordinate` included) never leave it, and its chat view ignores command nodes, so a command-only chat opened from the sidebar shows it too. Its header is hidden (`hideChrome`), so header actions don't show; `conversation.input.left` (the composer's row) does. A command's answer is drawn only once the chat has a message, and `command/executed` reaches only the window that ran it (a command the Host runs, such as the window's coordinate endpoint, sends none). **New Session differs by version:** 0.2.0-rc.2 reopens the workspace's unused new chat (so a chat already switched on comes back lit); 0.2.1-alpha.2 always makes a fresh chat (an unused coordinating one stays in the store, harmless).
- **Switching a DSH from projects to coordinator** (DSH Test first; live only on the user's typed yes in the split thread): this branch has no `plugins/projects`, so turning the `projects` row off isn't enough. With that DSH quit: in the profile's `package.json` replace the `dsh-plugin-projects` link with `"dsh-plugin-coordinator": "link:<checkout>/plugins/coordinator"`, and the name in `dsh.profile.bundles`; in `node_modules` remove the `dsh-plugin-projects` link and add `dsh-plugin-coordinator`; in `cordis.patch.yml` give the `projects` row's config (guardedTools, thread defaults) to a `- id: coordinator` row, leaving out `projects:`, `coordinator*`, `welcome` and the goal. Then type `/coordinate` in a chat. Rollback: quit, check out the old commit, put the profile back; `~/.dsh/projects` is never touched.
- DSH's session controller `prompt` doesn't run slash commands; only the commands service does (`commands.execute(agent, line, attachments, signal)`; the window's remote `commands/execute` takes `agentId`, `line`, `submittedAttachments`). It logs `command/run` and `command/done` in the chat, which is what the projection folds.
- A forked session's log starts with its source's events (`inheritedEventCount`, passed to a projection's `init`; DSH lists the fork under its source with `parentSessionId` and no `origin`). ### Gotchas (calendar)
- DSH checks tool arguments against strict JSON Schema: a `type: 'string'` parameter refuses null. `calendar_update_event` empties fields through `clear`, and an empty string means "not given", because weaker models send every field.
- The endpoints take `{args}` keyed by the method's parameter names, not positions.
- An approval's `reason` is only in the session log's `approval/asked` event (the bridge's summaries leave it out); `test/e2e/run.mjs` reads the log with its own zstd frame splitter.
- A Workspace Write turn that waits on approval never ends in a headless run: wait for `approval/asked`, then cancel it.
- Microsoft, and CalDAV servers that schedule (iCloud, Fastmail, Nextcloud), email a meeting's guests on every change its organizer saves, so such a change needs notify; Google emails only with `sendUpdates`. `SCHEDULE-AGENT=CLIENT` would hold a CalDAV server back, but it stays on the event and silently stops the server's scheduling from the user's other apps, so it isn't used.
- With approval policy 'never' (Full access), DSH turns a gate's `ask` into "the user rejected tool …", which misleads the model: the gate reads `approval.effectivePolicy(session)` and refuses with its own reason instead.
- `defineTool` keeps only the keys it knows: the `personal` mark goes on after it. The manager tests stand in for `@deepseek-ai/dsh-tools` with a `module.register` resolve hook to run the real tools.
- UTC and floating times show on the user's clock; only a named zone keeps its own.
- Google's `sendUpdates: none` still puts a meeting on its guests' Google calendars, changes it there and takes it off: that is contact, counted as `reaches`, not as nobody.
- The ToolExecution object itself is the same in the `tools/pre-execute` gate and in the tool's `execute(args, exec)` (dsh-tools' prepareExecution): `ShownPlans` keys the prompt's recipient list by it in a WeakMap. A provider can leave `callId` empty or repeat it.
- Graph gives no etag the plugin holds for a series it keeps only as occurrences, and Google none for an occurrence found by its start: a change there reads the event first and compares its people both ways (`otherPeople`), since no 412 would catch a guest added meanwhile.
- A change to one occurrence doesn't change the series' etag, on Google or Microsoft: a whole-series write reads the occurrences too (Google by uid, Microsoft's instances in the synced window), held etag or not. Compare like with like: the plan's records and the server's read must cover the same occurrences, or a change can stop again and again.
- The window's yes counts only for the same change (`asked.js` keys it by event, scope and fields, `notify` and `approved` aside): a Send must repeat the refused call's patch exactly, or the host asks again.
- A CalDAV server names the user by several addresses (mailto, `urn:uuid:`, the principal's URL or path); compare them with `addressKey`, never by mailto alone.
- A blank DSH window with the page error "scope 'session-maybe' rendered without an installed adapter" is DSH's own hot reload: when one of DSH's browser files (its session part, its sessions service or its renderer) changes on disk while it runs, even only its mtime or ctime, DSH swaps it in place and its root throws in the gap. The calendar never writes there. Don't write or touch a DSH install a test run is using; give each run its own (/mnt/project-files/calendar/blank-window/ has the trace and a repro). A hard-linked copy of an install (`cp -al`), or deleting one, changes the ctime of every file it shares, which is enough: make real copies (`cp -a`).
- The e2e's scripted model names every session after the tool it calls ("MISSING TOOL calendar_update_event"), so two calls of one tool share a title: ui.mjs renames a session it has to find again (the session bridge's `/sessions/:id/rename`).
