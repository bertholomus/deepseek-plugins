## Gotchas (things that broke, decisions made and why)
- DSH's composer pick (`session-controller selectModel`) saves the pick as DSH's default in the background (`agentDefaultModel.saveSelection`, a profile edit; the config is volatile, so no reload), and its window's catalog store refreshes only on `llm/adapters-updated`, `settings/document-updated` (emitted only when the settings page reads) and credential events. So nothing tells the window the default changed; the plugin infers it from a changed `modelSelection.next` of a loaded session (`followDefault`). The save can land after the first re-read, hence the retries.
- DSH's `Tooltip` clones its child (no wrapper element) and renders its bubble `position: fixed` (with `portal`, in `document.body`), so wrapping a grid item in it keeps the grid intact.
- DSH's `turn/end` (G5): `reason.kind` is completed, blocked, max-tokens, aborted, error, interrupted or forked. `aborted` carries `reason: {kind: user|parent|disposed|hook, reason?}`; DSH shows the hook `deepseek-account/signed-out` as a failure, so the plugin does too. `error` carries `{message, code}`, the message as `<HTTP status>: <JSON body>`. A cancel through session-bridge is `aborted`/`user`, so "Stopped" doesn't say who stopped it.
- The window's control stream starts with the sessions DSH has loaded; a thread that hasn't run since DSH started has no projection there until something reads it. Rows, cards, marks and hovers call `projects.refresh` (DSH's `refreshProjections`, cached per connection) once for each open thread, or a cold thread would read "No handback yet" instead of Failed.
- DSH's session-list hover card lingers on the previous row for a moment and opens the next after a delay, and DSH marquees a long title while its row is hovered (it scrolls the title span). Test scripts wait for the hovered thread's own card ("Thread t7 of").
- DSH's code changes (G4): the `workspace/changes` event carries only `{turn}`; DSH sets the turn's summary right after appending the event, so the plugin reads `workspaceChanges.summary(sessionId, seq)` a tick later (setTimeout 0, then up to 3 retries). DSH keeps summaries in memory until the session is disposed, so after a restart `api/changes.summary` is 404 and only the plugin's copy remains. Both versions' recorders are identical and also list file-tool edits outside git.
- DSH's Review tab (`dsh-resource://changes-review/session/<sid>/<seq>/<turn>`) reviews the session whose right sidebar holds it: its body uses the hosting session's id and takes only `seq` from the address. Opened from the coordinator it asked for the coordinator's seq and showed nothing. So `openReview` opens the thread, then calls `ctx.sidebarRight.openResourceIn(thread, address)` once `ctx.sidebarRight.actionsFor(thread)` is defined (DSH adopts the thread's sidebar a moment after it mounts; polled every 100 ms for 5 s). Both methods are on DSH's controller in rc.2 and alpha.2 but not on its `ISidebarRight` type; without them the thread just opens.
- DSH writes a session's projection cache at turn end, before the `workspace/changes` event, so the cache never has the thread's `changes` mark. Read live values with the web API `session/projections` (`{request: {sessionId}}` → `{asOfSeq, values}`), as the e2e does.
- DSH shows its "Edited N files" card only while Settings › General › **Show coding view** is on (`ctx.configForms.developerTools.enabled`, default off); the plugin follows the same switch (`codeChanges()`), on where DSH doesn't have it.
- Concurrent threads in one git folder each get the other's edits: DSH diffs the whole tree at each turn's end. In the judge's demo t2 (no edits) shows t1's Summary.tsx and t12/t13 both show both files. It matches DSH's own card, so it stays for now; a worktree per thread is the fix.

- DSH's file tools refuse to change a file the session hasn't read or written ("file has not been read"); the fake model makes one tool call per turn, so the e2e thread writes a new file, then edits it in a later turn.

- Never test on the live DSH: restart-needing plugin tests go to DSH Test (see Doing now). A live restart, even after the idle check, needs Albert's OK for that load.
- The cloud thread can't `send_message` to the Mac's Remote Control session ("receives only that person's own messages"). Steer it with `start_rc_session` instructions on the user's latest message; they arrive as "delivered" while it runs.
- DSH loads a plugin package only if the profile lists it in `dsh.profile.bundles`. A patch row alone does nothing. `dsh plugin --profile desktop add <path>` adds the link dependency, the `node_modules` symlink and the bundles entry. Use the `dsh` that DSH Desktop installs, because the npm `dsh` refuses the desktop profile. A running DSH doesn't load new bundles, so restart it.
- With the bundle listed, the bundle's own patch inserts the row. Configure it with an address row (`- id: projects` plus `config:`). An extra insert row duplicates the id. DSH still boots and the later (configured) row runs, because cordis-plugin-include indexes rows by id. That was checked on a real host.
- DSH's `installModelSelection` (dsh-agent) puts an `agent/request` listener on every API session at agent setup. It runs outside any plugin listener and replaces provider/model/effort with the session's selection, so a plugin's `agent/request` override is lost. Use `sessionController.agents.selectForNextRequest(agent, selection)` instead. It is internal: it is what `selectModel` does, minus saving the global default. The plugin falls back to a `{ prepend: true }` override when the method is missing (tested on the real host too).
- Do NOT use `sessionController.selectModel` for per-session models, because it also saves the selection as the global DSH default. session-bridge's `/sessions/:id/model` still has this side effect.
- cordis 4 has no optional inject. Use `ctx.get('llm')` or `ctx.get('agentDefaultModel')`, which return undefined when absent. `ctx.llm` without inject throws.
- `process.umask` is process-wide. A recursive `mkdir` under umask 0177 fails with EACCES for a normal user, but root skips the check, so cloud tests as root pass. Run folder tests as `nobody` too.
- Session events: prompts are `user/message` with `source.kind: 'user'` and the request id (`projects-…` for this plugin's own prompts). The Host also logs user-role messages with other kinds, such as `runtime-context` and `model-selection` notices. Don't treat those as prompts.
- `sessionController.prompt` treats any mode other than `steer` as a follow-up, so session-bridge's `followup` mode works even though the typed modes are `queue | steer`.
- Tools and system-prompt sections are registered on `agent.ctx` (agent-scoped), so only project sessions see them. The plugin hooks `agent/created` to attach on create and on every resume.
- `defineTool` validates enum params before `execute`, so a bad `status` comes back as INVALID_ARGS.
- Repo-local `node_modules` may be a symlink in cloud sessions. .gitignore's `node_modules/` does not match a symlink, so never `git add -A`.
- In the cloud Bash tool, `pkill -f <pattern>` also kills the tool's own shell when the pattern appears in the command. Find the PID with `ps -eo pid,args | awk ...`.
- Remote Control on the Mac refuses profile changes unless the user typed the approval in the thread. A relayed card tap does not count.
- DSH routes a linked plugin's `peerDependencies` (`@deepseek-ai/schemastery`, `@deepseek-ai/dsh-tools`) to its own install, so a plugin folder needs no `node_modules`. The e2e test proves it. The smoke tests still need the peers installed.
- After a DSH restart, an existing coordinator session stays cold until someone prompts it. The log says `coordinator <project> <session> resumed` when the plugin has checked it.
- DSH words the approval reason itself: `escalate sandbox to danger-full-access: <justification>`.
- Session titles: the session header keeps the creation-time title. Renames are `session/title` events.
- Per-thread caps don't bound a coordinator that starts new threads in a loop; `maxThreadsPerHour` does. Keep a project-level cap on anything a model can repeat.
- DSH's agent loop runs every queued message as its own turn (`turn/start` … `turn/end`) and only reports `idle` after the last one. Anything per turn must be read from the session log, not from status transitions.
- `sessionController.inspect` on a cold session uses the cold read, which appends synthetic `interrupted` turn closers for a turn a crash left open. Resuming the agent persists them. A crashed turn never produces a running → idle transition.
- A config save restarts the plugin (cordis `update` → `restart`): the old scope is disposed first, then `apply` runs again, while the old instance's async work keeps going. Hence the shared store and the coordinator lock.
- `ApiSessionNotFound` (session-controller) is the only error that means a session is gone; `inspect` can also time out or fail on I/O.
- Live config: a schemastery field marked `.volatile()` reaches the plugin as a reference with `get()`. When a save changes only volatile fields, the loader updates those references in place (no restart) and emits `loader/volatile-update` to the plugin. DSH's settings page (`@deepseek-ai/dsh-settings`) only offers forms for plugins with volatile fields. `index.js` guards with `live()` for a schemastery without `.volatile()`.
- Browser halves: `package.json` `dsh.client: { platform: 'web', inject: [...] }` plus `exports["./client"]`. The file is a classic script calling `window.__ModuleLoader__.load({ id, factory: (require) => ({ inject, apply }) })`; `require` gives `react` and `@deepseek-ai/dsh-client-ui-primitives` (SettingsFormModel, SettingsForm, SegmentedControl, ...). DSH concatenates browser halves into one script, so a syntax error breaks other plugins too: always `node --check lib/client.js` (the e2e also parses what DSH serves).
- The plugin's page slot is `plugins.bundle.config`, keyed by package name; it gets no form prop, so the client builds one from `ctx.configForms.get('projects')`. Register inside `ctx.configForms.whileServed(['projects'], ...)`.
- DSH's config editor refuses to save a row whose id is in the profile twice (bundle insert + profile `insert:`): it appends an address row, then its check reads the first (bundle) row and fails. The runtime still uses the later row, so only saves break.
- DSH reloads the profile patch on change for every profile (dsh-base's `hmr` row, on whenever there is a profile). There is no `patchReload` option in 0.2.0-rc.2.
- Playwright: `page.goto(..., { waitUntil: 'networkidle' })` hangs on a second load of the DSH web app (it keeps a live connection). Use `domcontentloaded` plus a short wait.
- DSH hides a session that never had a turn: the list's `blank` stays true until the first `turn/start`, and the web client drops blank sessions from the sidebar and search. Hence the coordinator welcome.
- Settings → Plugins: a component shows "Not running" when its loader entry has no fiber (`fiberPhase: null`): the module failed to import (cordis-plugin-loader `Entry._init` logs the error and returns), the row is disabled, or there is no entry with that id. Its switch is locked when there is no entry, or when the id is in the composed profile twice (`listPlugins` marks it `unaddressable`). With a duplicated id the loader still makes one entry from the later row (`EntryGroup.update` keys rows by id), and that entry runs.
- An import failure shows only on the host's stderr: `dsh: warning: 1 entry did not activate` / `<id> (<package>): failed to import`. DSH Desktop's host stderr isn't in a file the Mac session found. `dsh-plugin-doctor.mjs` reproduces the import read-only with the exact error.
- Session logs are `~/.dsh/sessions/<workspace>/<session>/session.v4.jsonl.zstd`: zstd frames appended one after another, each holding JSONL events (`{type, seq, time, data}`). Node's `zlib.zstdDecompressSync` (and its stream) decode only the first frame, so split frames first (`dsh-idle.mjs` walks the frame headers). DSH writes the log only at checkpoints (before each model request and tool dispatch, and at turn end), so a log's mtime says nothing about a long model call or tool still running; read the turn events instead.
- Tool calls and results are in the session log: `tool/call {callId, name, arguments}` and `tool/result {message: {toolCallId, content}}`. The idle review finds a handback by its result text, which starts with "Handback ".
- A project's coordinator and threads run tools in `workspacePath`. If that is the folder DSH loads a plugin from, their pulls and edits change what DSH loads at the next restart. Changing `workspacePath` later doesn't move an existing coordinator: DSH resumes a session in the cwd from its header, so only new threads would move.
- Avoid `dsh --dump-config` on a live profile: `loadProfile` removes link projections and rewrites `cordis.yml`. The doctor doesn't.
- DSH's markdown draws a relative link (`[t](.dsh-thread/t3)`) as a file button titled with the path, and a click opens `dsh-resource://file/session/<sid>/<path>` in the right sidebar with no tab kind. A tab type in the `extension` band with a matching pattern outranks the builtin file viewer; that's how thread links open threads.
- Slot keys: right-sidebar tab bodies and titles are keyed by the tab type's `id` (not its kind). Embedded chats follow DSH's subagent pattern: a resource that `sessions.retain`s the session, a tab body wrapping `SessionProvider` around its own child slot (declared in `children` with `scope: 'session'`), and `renderFactorySlot('conversation.content', {variant: 'embedded'}, {slots: {views}})`.
- DSH saves projection state per session in `DSH_HOME/storages/session_projcache/sessions/<id>.json` (`record.rows.<key>.val`), written at every turn end; the e2e reads the window's view there.
- `conversation.chat.turnTail` only renders under completed turns, and tool rows fold away when a turn completes, so per-turn cards go in the turn tail, not in tool views.
- Headless Chromium draws DSH's translucent menus without the blur, so menus look see-through in screenshots; DSH's own menus look the same there. For screenshots that match the app, launch the full Chromium (`/opt/pw-browsers/chromium-1194/chrome-linux/chrome`) with `--enable-unsafe-swiftshader --use-angle=swiftshader --enable-gpu-rasterization`: it draws the blur.
- In the cloud Bash tool, `pgrep -f`/`pkill -f` match the tool's own shell too. Keep a pid file (`echo $! > demo.pid`).
- A scripted model must match only the user's own text: handback tags carry thread titles, so a demo model that started a thread whenever it saw "inventory" looped until `maxThreadsPerHour` stopped it.
- Plugin endpoints for the window: a host object with `typertRemote = bindTypertRemote(this, SERVICE, {namespace})` and `Remote(...)` markers on its prototype methods (what DSH's `@Remote` decorator does), provided with `scope.provide(SERVICE, obj)` inside `ctx.inject(['typertGateway'])`. The gateway reads parameter names from the method source, so use plain identifiers (not `agent`, `session`, `workspaceFileScope`). Wire: POST `api/<ns>/<method>` with `{type:'client-request', rpcId, method, payload:{args}}`; the client calls `ctx.connection.rpc.call('/api', '<ns>/<method>', {args})` and gets `{ok, value}` or `{ok:false, error}`; it throws "transport failure … HTTP <status>" when the endpoint is missing (an older host). `RemoteError(code, message, details)` keeps its code; any other error becomes `gateway/internal`.
- DSH's `session/selectModel` takes `{request:{sessionId, provider, model, reasoningEffort?}}` and also saves the DSH default model. Every selection (the plugin's own too) reaches agent-scoped `session/event` listeners as `model/selection`; the plugin remembers its own (`ownSelections`) to tell them from the user's picks.
- React in DSH's browser halves: `props.children` is a single element when there is one child, so never spread `...children`; pass `children` as is. The smoke tests' fake React always gives an array, so only a real window catches it.
- DSH's composer picker CSS (`dsh-client-ui-model-selection`, not exported): the search placeholder is `--dsw-alias-label-caption` (the Input primitive's own placeholder color is much dimmer); the brand color `--dsw-alias-brand-primary` is near-black/near-white, the DeepSeek blue is `--dsw-alias-state-business-primary`.
- Effort checks have three modes (`checkSelection(catalog, model, effort, {fit})` in `lib/settings.js`): `false` refuses an effort the model lacks (used when an effort is set outright with `project_settings` or `project_thread_update`, so the coordinator hears the choices); `'known'` fits an effort some model offers and refuses an unknown one (an explicit effort at a thread start); `true` never refuses over effort (inherited efforts and every request). Fitting picks the highest level the model offers at or below the one asked, else its lowest.
- DSH's default model is whatever was last picked in any chat (`session/selectModel` saves it). `catalog()` overlays the live `agentDefaultModel.currentSelection()` on the catalog's `default`, because the model catalog's own default can lag behind a pick.
- DSH draws a `user/message` whose `source.kind` isn't `user` as a context notice; the one that woke a turn is a collapsed turn trigger. Its title is fixed by kind (`agent-message` → "Task message received" with a paper plane, `cordis-host-runner` → "Plugin status updated"); a plugin can't name it.
