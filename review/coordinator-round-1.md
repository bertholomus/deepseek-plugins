## Findings (most severe first)

1. **Minor, but it misleads the owner about what a thread did: a held handback reads as none after `/coordinate off`, and the stop message overstates what runs.** Where: `lib/client.js` line 2277 (`told ?? (entry.resolved ? 'Resolved' : 'No handback yet')`) and `lib/projects.js` line 1528. What: t5 handed back while its chat wasn't coordinating (log: `handback … status=done chars=233 held`); its row in the Threads menu read "Idle · No handback yet" until `/coordinate` (picture 18). The command's answer said "Its 5 threads keep running" when one was running and four were idle; the e2e check at `run.mjs` line 693 asserts that wording. Fix: show a held handback as "Done · held until you coordinate again" (as the paused case does with "held until you resume"), from the store's pending handbacks; say "Its 5 threads stay (1 running); what they hand back waits until you run /coordinate here again."; check both in the window e2e.
2. **Minor (reliability): a handback whose answering turn DSH cut off is never raised again.** Where: start-up (`ProjectManager` resume and catch-up). What: t4's needs-decision handback was delivered at 3:05:10; the chat's turn taking it was cut by the restart at 3:05:16 and closed as interrupted; after the restart the chat sat idle with an unanswered handback, and only DSH's "Task stopped" and the card showed it (picture 05). The chat answered it only when I next wrote. Fix: at start, when a coordinating chat's last turn ended interrupted with a handback or note in it that it never answered, give the chat the plugin's one-line note again ("DSH closed while you were reading this handback: reply now"), once.
3. **Minor (reliability): a store file that fails to parse is silently replaced.** Where: `lib/store.js` `load()` (line 136) and `save()` (line 147). What: a cut-short `coordinator.json` loads as no chats, and the next write overwrites it: in my probe a chat, its thread map and a held handback were gone, no copy kept and nothing logged; a failed save is swallowed too. Writes are atomic (tmp and rename), so this needs an outside cause (a full disk, a hand edit, a bad copy), but then every chat loses its threads, its nesting and its held handbacks without a word. Fix: keep the unreadable file as `coordinator.json.unreadable-<time>`, log `store-unreadable` and `store-save-failed`, and name it on the plugin's page.
4. **Minor (UX, in a safety prompt): the delete prompt cuts the path from its start, so it hides what goes.** Where: `lib/deletes.js` line 138 (`word.slice(0, 59)`). What: "This command deletes /Users/albertlee/Projects/goal95/judge/coordinator-r1/ws/RE… (rm)" (picture `s2-approval-1`); the README's example is "deletes build/ (rm)". The command shown below the sentence saves the owner, and the same cut text goes to the chat and the thread. Fix: say the path relative to the thread's folder when it is inside it, and cut long paths in the middle, keeping the last part.
5. **Minor: the chat is not told when the owner answers a thread's prompt, so it can repeat a stale state.** Where: the roster (`## Threads` section) and the approval note. What: I rejected t4's delete at 2:59:46, and the plugin logged it then (`declined …/t4 bash`), but the chat heard of it only in t4's handback at 3:05:10; in between, its reply after t3's handback (3:00:42) told me t4 was "waiting on your approve/reject of its `rm`", and its roster said only "running · no handback yet". Fix: when DSH records the answer (`approval/decided`), put it on the thread's roster line ("you declined its rm at 2:59 PM; it will hand back") so the chat's next reply is right.
6. **Minor: the delete check misses moving a file out of the folder.** Where: `lib/deletes.js` `deletesOf`. What: `mv README.md /tmp/` passes the check, so only DSH's sandbox stands between it and the file leaving the folder (Workspace Write writes "DSH's temp folders" without asking, README line 156), and the README's list of what doesn't count (line 301) names `>`, `git reset --hard`, `git checkout .` and `rsync --delete` but never `mv`; `truncate -s 0`, `sed -i d` and `cp /dev/null` pass too. The send check misses Perl's LWP post and `openssl s_client` (covered by "a program it doesn't know"). Fix: count `mv` (and `rsync --remove-source-files`) with a destination outside the thread's folders as a delete of the source, or list it in the README.
7. **Minor: a thread's shell edits drop out of its counts whenever another thread works in the same window.** Where: `lib/projects.js` `shellEdits` (line 2525), which drops a turn's whole shell diff when `Mutations.overlapped` (`lib/shell.js` line 290) sees another session's write in the window. What: t2 created `notes/reversed.txt` with a shell command while t1 ran; the log has `shell-window … turn=1 shared` for both and no `changes` line for t2, so its cards and rows show no changes at all (picture 06), though its handback says it made the file. t5, alone later, counted its shell edit (`files=1 +3 -0 shell=1`). Documented ("a turn that overlaps another session's work counts nothing for its shell"), but parallel threads in one folder are the plugin's main use, so the counts are missing exactly when there is most to count. Fix: per-thread worktrees (the README's Not yet), or count by the paths the thread's own commands wrote.
8. **Minor (switched off): dead thread tabs and file links.** Where: the right-sidebar thread tab and the `.dsh-thread/tN` links. What: switched off in Plugins, an open thread tab shows DSH's "Nothing here can view this kind of content yet." and the chat's thread links are drawn as file links to `.dsh-thread/tN` (picture 20). Known to the builder. Fix: on dispose, close the plugin's own tabs or swap them for DSH's chat tab of the thread's session; say in the README what the old links do while off.
9. **Nit:** the plugin's page and Thread settings name config keys and files ("guardedTools in this plugin's config", "cordis.patch.yml", `- id: coordinator`); screen-reader names carry thread ids ("Add subtract to calc.py (t1): …").
10. **Nit:** pause and resume both log `settings <chat> paused` (`projects.js` line 3658 logs the keys, not the values), so the log can't tell them apart; and a wrong live setting (`threadPermission: 5`) is named on the page but never in the log (only the fixed keys log `config-problem`, `index.js` line 120).
11. **Nit:** the README says the plugin's text "reads at 4.5:1 or better … in light and dark", but no test measures contrast; nothing is shot with Wallpaper on, though the owner runs it; the bar above the message box has no reduced-transparency rule of its own.
12. **Nit (docs):** the README is 330 lines and 69 KB; single bullets run long (A thread's Changes 678 words, the send check 575, Session list 515, the delete check 417, Threads menu 369). It reads as a complete reference but is hard to scan for one answer.
